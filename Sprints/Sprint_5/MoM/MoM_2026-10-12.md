## 2. Key Discussion Points
- **What the SDK Has to Do:**  
  The team restated the goal. Engineers publish, subscribe to, and query signals from Python with numpy arrays. The SDK wraps the existing client and does not reimplement it. The client code stays unmodified. A crash in the client should raise a Python exception, not end the process, and version drift should be caught at build time instead of by users.

- **Go Section (Lucas):**  
  Three problems came up with every approach that was tried. Go generics are fixed when the code is compiled, so Python needs a type table written by hand, with 16 encodings. Callbacks run on the library's own thread while it holds its locks, so a callback that calls back into the library hangs, and Python has to pull batches from a buffer instead. The Go runtime cannot be forked or reset, so it has to run in its own process. In one benchmark run, per-sample callbacks managed about 365 thousand per second in-process against about 15 million buffered. The bridge process costs about 17 MB per client and about 60 microseconds per call. Every library change means checking the type table, the 25 bridge calls, and Python by hand.

- **C# Section (Genevieve):**  
  The C# comparison used the same three questions. How are types shown to Python, who owns the thread that calls back, and what happens to Python when the library fails. Hands-on testing with SEL's C# client (issue #36) still needs the client on the team's machines.

- **Bridge Hardening and Demo App (Lucas):**  
  Since September 28 the bridge was changed so it survives its own crash. With automatic restart on, subscriptions resume from the last timestamp with no gaps or duplicates. A duplicate client name, a forked child process, and a timeout now each give a clear Python error. A local demo app shows publishers, the hub, and subscribers, and has a button that kills the bridge to show the recovery.

- **Open Decisions Put to the Client:**  
  The team proposed freezing the ctypes and cffi transports and keeping the bridge, targeting Linux x86_64 and aarch64 plus Windows x86_64 on Python 3.10 to 3.13, and keeping the current Python names for the API. The team also asked for access to a real Signal Hub for contract tests.
