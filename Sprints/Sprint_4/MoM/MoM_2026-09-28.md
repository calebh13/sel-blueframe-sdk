## 2. Key Discussion Points
- **Code Access:**  
  Genevieve got access to the C# and C++ versions of the client and pulled the Go client out of the server code. Caleb set that up as a private repository the team can work in. This removed the access blocker that held up Sprints 2 and 3.

- **CGo Findings (Caleb):**  
  The original plan was to add export headers to Go functions with a script and call them from Python through CGo. That turned out to be much harder than expected. Building Go as a shared library loads the whole Go runtime into the Python process. Go generics cannot be exported, so every generic call needs a concrete version written for each data type. Callbacks run on Go threads and need Python's GIL, which can stall or deadlock the client. Go objects cannot be handed to Python directly, so object lifetimes have to be tracked by hand. A panic in Go takes down the Python interpreter.

- **Bridge Prototype (Lucas):**  
  Three ways of calling the Go client were prototyped for publish and subscribe. Two load the Go library into Python (ctypes and cffi). The third runs the Go code as a separate process and talks to it over gRPC on localhost. All three worked for the basic operations, and short benchmarks showed similar throughput. Latency was around 5 ms for all three, which comes from the client's own send interval.

- **Failure Behavior:**  
  The big difference showed up under failure. When the Go code crashes or exits, the two in-process versions kill the engineer's Python session with no error message. The subprocess version only loses the child process and raises a normal Python exception. In-process versions also hang when Python code uses fork-based worker pools.

- **Why Go Is a Poor Fit:**  
  Most of the work so far has gone into glue code instead of features. Generics, background goroutines, panics, and blocking calls without timeouts all need special handling. Go also cannot call functions by name at runtime, so every exposed function needs a handler written by hand or generated. Keeping that in sync with the Go client would bring back the double maintenance Joe wants to avoid.

- **C# as an Alternative:**  
  Genevieve's research into Python.NET suggests the C# client may be easier to wrap. .NET keeps type information at runtime, so Python.NET can call C# classes and generic methods without an export layer. This still needs to be tested against the real C# client.

## 3. Decisions Made
- The in-process approaches (ctypes and cffi) are not safe enough for engineers to use.
- If the Go client stays as the base, the subprocess bridge is the approach to build on.
- The C# client with Python.NET will be evaluated before committing to either option.
- The Go client code will stay unmodified. The wrapper works around its behavior.
- Prototype code stays in the private repository because the client is SEL Confidential.
