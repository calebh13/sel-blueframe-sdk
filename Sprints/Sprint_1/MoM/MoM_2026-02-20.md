Notes:
Tyler gave an overview of SignalHub and explained that it is a custom message bus designed for efficiently moving large streams of data between a small number of endpoints. Unlike systems like RabbitMQ or NATS, SignalHub is optimized for high-throughput source-to-destination streaming rather than guaranteed message delivery or fan-out.
SignalHub was originally designed for fixed-rate data, where signals are sampled at regular intervals and sent in batches. Many automation use cases behave differently and are variable-rate, meaning updates occur when values change, with periodic full snapshots. SignalHub supports both fixed-rate and variable-rate data, with configuration typically handled at the signal or channel level.
Channels are used to group related signals together, similar to a struct. This reduces bandwidth and helps keep related values together. Internally, SignalHub can still multiplex and route individual signals, so channel continuity is not guaranteed unless specific alignment options are enabled.
A large part of the discussion focused on automation signals. Automation signals bundle multiple pieces of information that need to stay aligned: the primary value, a trigger timestamp, metadata about value quality, and metadata about time quality. This is important because consumers often need to know not just the value, but when it occurred and how trustworthy both the value and timestamp are.
Because SignalHub routes signals independently, there is no guarantee that different automation signals will arrive at the same time. In RTAC and other automation environments, logic is evaluated in processing cycles and expects a coherent view of system state. This means consumers will likely need to cache the latest values of all automation signals and process them together locally rather than assuming everything arrives in one push.
SignalHub uses a raw TCP binary protocol rather than HTTP to avoid overhead. There are existing clients in Go and C#, but no Python client. A previous C client exists but is outdated. The Go client is the best reference for any future Python implementation, though careful handling of binary encoding and session state will be required.
The difference between status data and control signals was also discussed. Status data is typically buffered and sent in batches, while control signals (such as commands to trip breakers or change setpoints) need to be flushed through the system immediately with minimal latency. Control signals may require slightly different channel configuration.
Decisions / Takeaways:
The project should focus on automation signals as the primary use case. Any SDK or tooling will need to handle subscription configuration, local caching of signal values, and batch processing. Initial development should focus on static configuration and core functionality rather than advanced features.
