## 2. Key Discussion Points
- **SignalHub Overview:**  
  Tyler gave an overview of SignalHub, explaining that it is a custom message bus designed for efficiently moving large streams of data between a small number of endpoints. Unlike systems like RabbitMQ or NATS, SignalHub is optimized for high-throughput source-to-destination streaming rather than guaranteed message delivery or fan-out.

- **SignalHub’s Flexibility for Fixed and Variable-Rate Data:**  
  SignalHub supports both fixed-rate (where data is sampled and sent in regular intervals) and variable-rate (where updates occur when values change) signals. Configuration is typically handled at the signal or channel level.

- **Channel and Signal Structure:**  
  Channels group related signals together, similar to a struct, which reduces bandwidth and helps keep related values together. Internally, SignalHub can still multiplex and route individual signals, so channel continuity is not guaranteed unless specific alignment options are enabled.

- **Automation Signals:**  
  Automation signals bundle multiple pieces of information: the primary value, a trigger timestamp, metadata about value quality, and metadata about time quality. This is important because consumers often need to know not just the value, but when it occurred and how trustworthy both the value and timestamp are.

- **SignalHub’s Behavior in Automation Environments:**  
  SignalHub routes signals independently, meaning there’s no guarantee that related signals will arrive at the same time. In RTAC and other automation environments, logic is evaluated in processing cycles and expects a coherent view of system state. Consumers will need to cache the latest values of all automation signals and process them together locally, rather than assuming everything arrives in one push.

- **TCP Protocol vs. HTTP:**  
  SignalHub uses a raw TCP binary protocol to avoid HTTP overhead. There are existing clients in Go and C#, but no Python client yet. The Go client is the best reference for any future Python implementation, although care must be taken with binary encoding and session state.

- **Status vs. Control Signals:**  
  Status data is typically buffered and sent in batches, while control signals (such as commands to trip breakers or change setpoints) need to be flushed through the system immediately with minimal latency. Different configurations may be required for control signals to ensure timely delivery.

## 3. Decisions Made
- The project will focus on automation signals as the primary use case for the Python SDK.
- The SDK will need to support subscription configuration, local caching of signal values, and batch processing.
- Initial development will prioritize static configuration and core functionality, with advanced features to be added later.
