Purpose:
Walk through SignalHub protocol documentation and explain how the System Graph is used for discovery and configuration.
Notes:
Tyler walked through the SignalHub protocol documentation and explained the basic session flow. A client connects over TCP, optionally sends a hello packet for negotiation, defines channels and signals, and then enters a read/write loop. Connections should be cleanly closed to avoid leaving server-side resources allocated.
The packet rate configuration controls how frequently the SignalHub pushes buffered data to subscribers. A common value is around 10 times per second, which results in roughly 100 ms update intervals.
Several protocol details were highlighted as important for any future Python implementation. All data is big-endian. Packets are sent as atomic units and must not be interleaved. Reconnection attempts should include some backoff to avoid overwhelming the system during outages. Publishing data significantly out of order in time can result in dropped data or the connection being terminated.
SignalHub can integrate with a historian service to replay historical data. It also keeps a small in-memory cache of the latest values. For an initial implementation, it was suggested to avoid relying heavily on historian features unless required by a specific use case.
Time alignment options were discussed again in the context of automation signals. When enabled, SignalHub can ensure that all parts of an automation signal are delivered together, as long as they were published with matching timestamps and configured within the same channel.
The System Graph was introduced as the mechanism for discovery. Publishers are expected to publish signal metadata to the graph so that consumers can discover what signals exist. Consumers can query the graph using an internal HTTP API for one-time queries, or maintain a session to receive updates when the graph changes. Graph state is session-based, so tearing down and republishing state is often simpler than trying to update individual entries.
Measurement points and quantities were discussed as a way to configure subscriptions without hardcoding signal IDs. This allows consumers to subscribe to data based on location or type rather than specific identifiers. This approach may be useful in the future but is not required for an initial version.
The automation signals documentation was reviewed briefly. Each automation signal consists of four related signals with standardized naming and binary encoding. Data types are optimized for efficient transport and do not include strings; enums or integer mappings are used instead.
Decisions / Takeaways:
Initial development should focus on core subscription, decoding, caching, and processing of automation signals. More advanced discovery and dynamic configuration can be added later if needed.
