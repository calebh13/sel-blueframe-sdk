## 2. Key Discussion Points
- **SignalHub Overview:**  
  Tyler gave an overview of SignalHub, explaining that it is a custom message bus optimized for high-throughput data streaming between a small number of endpoints. It differs from systems like RabbitMQ or NATS as it prioritizes throughput rather than guaranteed message delivery or fan-out.

- **SignalHub’s Flexibility for Fixed and Variable-Rate Data:**  
  SignalHub supports both fixed-rate (where data is sampled and sent in regular intervals) and variable-rate (where updates occur when values change) signals. Configuration is typically handled at the signal or channel level.

- **Channel and Signal Structure:**  
  Channels group related signals together to reduce bandwidth and ensure related values stay together. While channel continuity is not guaranteed, individual signals can be multiplexed and routed independently.

- **Automation Signals:**  
  Automation signals bundle several pieces of information: the value, a trigger timestamp, and metadata about value and time quality. This is essential for consumers that need to know the exact moment a value was recorded and the trustworthiness of the data.

- **SignalHub’s Behavior in Automation Environments:**  
  SignalHub routes signals independently, meaning there’s no guarantee that related signals will arrive at the same time. This requires consumers to cache the latest values and process them locally, rather than assuming synchronous updates.

- **TCP Protocol vs. HTTP:**  
  SignalHub uses a raw TCP binary protocol to avoid HTTP overhead. There are existing clients in Go and C#, but no Python client yet. The Go client is the best reference for any future Python implementation, although care must be taken with binary encoding and session state.

- **Status vs. Control Signals:**  
  Status data is buffered and sent in batches, while control signals (such as commands) require immediate transmission with minimal latency. Different configurations may be needed for control signals to ensure timely delivery.

## 3. Decisions Made
- The project will focus on automation signals as the primary use case for the Python SDK.
- The SDK will need to support subscription configuration, local caching of signal values, and batch processing.
- Initial development will prioritize static configuration and core functionality, with advanced features to be added later.
